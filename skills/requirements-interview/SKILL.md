# 需求访谈（requirements-interview）

> 状态：**draft**（Phase 2 实现时完善；本文件当前仅确立流程骨架，供 registry 演示格式）
> 依据：规范 §5.1–§5.3

## 目标

把用户的自然语言想法转化为结构化需求（PRD/用户故事/验收条件），全程可追溯；用户不需要掌握技术术语。

## 流程骨架

1. **先理解再追问**：目标、使用者、业务问题、成功标准 → 区分「已确认事实 / 用户偏好 / 推断 / 待确认」。
2. **一次一问**：每次只问当前最重要的一个问题；根据答案动态调整，不重复询问。
3. **选项化**：给出 2–4 个易懂选项并说明影响；拒绝术语化提问。
4. **矛盾与假设**：识别矛盾、模糊词、隐藏假设；主动覆盖异常、权限、数据一致性、并发、边界；未经确认的重大业务规则标记为「临时假设」继续规划，不得当事实。
5. **落盘**：每项需求唯一 ID；产出结构化文档（草案 + 开放问题清单），非聊天记录。
6. **摘要确认**：简明摘要请用户确认；确认后需求状态才可进入 APPROVED（§5.3）。

## 输入 / 输出

- 输入：用户想法（自然语言）、既有材料（可选）。
- 输出：`requirements/` 下的结构化需求文档、`traceability.csv` 初始矩阵、开放问题清单。

## 边界（禁止）

- 不得替用户确认关键业务规则。
- 需求不清时不得让开发角色自由猜测并大规模编码。

## 验收（P2 实现时）

- 与模拟用户的两轮访谈能产出结构化草案（P2-1 验收标准）。
- 未经确认的关键需求导致工作流阻塞（Phase 2 门禁）。
