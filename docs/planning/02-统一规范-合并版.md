# AI 自主软件研发平台：统一规范（合并版 v1.0）

> 文档用途：本文件是《第一个.md》（【甲】）与《第二个.md》（【乙】）的合并版，是平台建设的**唯一执行基准**。冲突裁决依据见《01-冲突与遗漏分析.md》，冲突处以本文件为准。
>
> 适用对象：负责实现本平台的 AI 编程工具或开发团队。
>
> 核心目标：用户描述一个软件想法后，平台通过需求澄清、架构设计、任务编排、规范化编码、自动化测试、代码审查、集成修复和交付验收，尽可能自主地产出可运行、可维护、有证据的标准软件项目；平台本身最终构建为可安装的本地桌面软件。

---

## 1. 最高优先级指令

1. 你不是在做一个"多角色提示词集合"或聊天 Demo，而是在建设一套具备明确流程、执行约束、工具接入、状态管理、质量门禁和交付能力的 **AI 软件研发控制平台**。
2. 先合并规范、检查冲突、制定实施计划并获批准，再开始编码；不允许先自由生成大量代码再靠重构补救。
3. 流程由系统控制，不只靠提示词提醒：角色可以建议，但不能自行跳过强制阶段或宣布门禁通过。
4. 每个阶段必须实际创建文件、运行检查、记录证据；不得伪造测试通过、构建成功、部署成功、审查通过、模型连接或技能安装成功。
5. 无法执行的验证必须标记为"未验证/受环境限制"，说明原因和可复现命令，不得标成通过。
6. 目录已有内容时先识别，不得未经许可覆盖或删除；不得执行危险的全局安装或清理。
7. 需求澄清阶段必须与用户互动；进入已批准的实施阶段后尽量自主执行，在失败、需求冲突、危险操作或需要授权时暂停。
8. 非关键细节提出合理默认值、记录假设并继续推进；重大架构分歧、重大成本或不可逆操作必须询问用户。
9. 不做虚假宣称：模拟模式不得称为真实多模型并行；"本地安装"不得等同于"完全离线"；生成代码不得作为语言支持完成的证据。
10. 若某项要求不适合当前实现阶段，登记为后续任务并解释原因，不得静默删除关键目标。

## 2. 术语与核心概念

| 术语 | 定义 |
|---|---|
| 平台 / 平台自身 | 本文件要建设的 AI 软件研发控制系统本身 |
| 用户项目 | 平台根据用户想法生成的目标软件项目 |
| 角色（Role） | 一组职责、输入、输出、权限与验收要求的逻辑配置；**不要求**一个角色对应一个独立模型或进程，同一模型可在不同上下文承担多角色 |
| Agent 运行（AgentRun） | 某角色在某个任务上的一次实际执行，含输入、输出、模型调用与证据 |
| Skill | 可复用的专业工作流与知识包（SKILL.md 格式），不是模型，也不等于角色；一个角色可用多个 Skill，一个 Skill 可服务多个角色 |
| 质量门禁（Gate） | 由系统执行器依据机器检查结果判定的阶段/任务准入条件，不是提示词 |
| 证据（Evidence） | 命令、退出码、工具版本、日志、报告产物等可复查的客观记录 |
| 工程标准执行引擎（ESEE） | 把项目规范转化为可执行检查并强制应用到每个任务的核心子系统 |
| 本地安装 | 平台应用安装在用户电脑上；≠ 本地推理（调用本地模型），≠ 完全离线（模型/依赖/文档全部无网可用） |
| 不可信输入 | 外部网页、仓库、Skill、脚本、生成代码、模型输出等一切未经审查的内容 |

## 3. 产品定位与成功标准

### 3.1 产品定位

以自然语言想法为入口、以标准化软件工程交付为目标的多智能体研发控制平台，管理软件从概念到交付的完整生命周期：

1. 与用户进行需求访谈和确认。
2. 生成产品需求、用户故事、验收条件和非功能需求。
3. 技术选型、架构设计、接口/数据模型设计和风险分析。
4. 拆解为依赖清晰、粒度适当、可独立验收的任务。
5. 按语言、框架、模块选择合适的角色与 Skills。
6. 在统一规范下开发前端、后端、数据库、接口、测试和部署配置。
7. 静态检查、代码审查、测试、安全检查、依赖审计和构建验证。
8. 失败诊断、修复、重测和回归验证。
9. 通过受控部署流程完成交付。
10. 输出文档、运行方式、测试证据、已知限制和维护指南。
11. 沉淀经过验证的规范、组件、方案为可检索的知识资产，避免重复造轮子。
12. 最终形态为可安装的本地桌面应用（Windows 优先）。

### 3.2 "一个想法做出标准项目"的最低定义

不能把"生成了代码"视为成功，至少应具备：完整可追溯的需求与验收标准；明确的架构、模块边界和接口契约；可维护的目录与配置；可复现的依赖安装、构建和启动方式；合理的数据模型、迁移、错误处理和日志；自动化测试与可查看报告；风格/类型/静态/安全检查；README、架构、API、配置与部署文档；不含真实密钥的环境变量模板；关键功能的实际验证证据；对无法完成功能和风险的如实披露。

标准按项目类型与风险等级调整：不把微服务强加给小脚本，也不因项目简单跳过必要测试与交付文件。

### 3.3 能力边界（必须如实告知用户）

- 角色可以是同一模型的不同任务配置，也可以由不同模型承担。
- 平台能力受模型质量、工具权限、运行环境、知识准确性、资源预算和需求清晰度影响。
- 本地安装 ≠ 完全离线；多角色协作 ≠ 没有缺陷。
- 可靠性由工程规范、自动化检查、独立测试、权限控制、审计和人工审批共同实现。

## 4. 设计原则

1. **先定标准，再写代码**：规范先行并配置化，不允许先编码后补规范。
2. **流程由系统控制**：项目状态机、任务依赖图、准入条件、失败回退由执行器强制，不依赖 AI 自觉。
3. **规范可执行、可验证**：每项重要规则对应模板、配置、自动检查、测试或验收证据；无法自动检查的必须显式标记为"人工/AI 审查项"。
4. **任务小而可验证**：依赖明确、增量交付，先可运行骨架再逐步验收。
5. **接口先行，有条件并行**：并行开发必须以已确认的接口契约、数据模型和版本约束为依据。
6. **测试结果优先于 AI 自我评价**：阅读代码不等于运行测试；"AI 认为没问题"不等于通过。
7. **知识与技能需要治理**：外部 Skill、SDK 示例、历史代码必须审查、分类、版本锁定并验证。
8. **交付要有证据**：源码、构建结果、测试结果、运行说明、已知限制齐全，不得伪造成功状态。
9. **最小权限与授权**：默认最小权限、秘密不入库、危险操作需明确授权。
10. **自动化程度逐步提高**：对删除数据、访问敏感信息、执行不可信脚本、部署生产等操作按风险分级审批。
11. **一切流程可暂停、恢复、重试、取消、审计和定位失败原因。**

## 5. 用户交互与需求管理

### 5.1 用户的角色

用户是需求提出者、业务规则最终确认者和高风险操作授权者，不应被要求掌握技术术语。系统主动识别缺失信息，逐步确认业务流程、权限、数据规则、异常场景、性能要求、部署环境和验收方式。

### 5.2 需求访谈规则

- 先理解目标、使用者、业务问题和成功标准。
- 区分已确认事实、用户偏好、推断和待确认事项。
- 一次优先询问一个最重要的问题；根据答案动态调整，不重复询问。
- 识别矛盾、模糊词和隐藏假设；主动询问异常、权限、数据一致性、并发和边界。
- 必要时给出 2–4 个易懂选项并说明影响。
- 需求整理为结构化文档而非聊天记录；每项需求设唯一 ID，任务、代码、测试可追溯。
- 未经确认的重大业务规则不得静默当成事实；可用显式标记的临时假设继续规划。
- 最终用简明摘要请用户确认。

### 5.3 需求状态机

`DRAFT → INTERVIEWING → REVIEW_REQUIRED → APPROVED → IN_IMPLEMENTATION → VERIFIED → DELIVERED`

允许因需求变更回到评审，但必须记录变更原因、影响范围、成本、受影响任务和回归测试要求。

### 5.4 需求文档与追踪

需求文档至少包括：项目目标与背景；目标用户与场景；功能范围与明确不做的内容；用户故事及验收条件；业务规则和状态转换；页面/命令行/API 交互需求；数据实体、字段、约束、关系和保留策略；权限模型与审计要求；异常与边界；性能、可靠性、安全、可访问性等非功能要求；部署环境与运行限制；外部系统、API、SDK 和数据源；验收计划、风险、假设和待确认事项。

建立 `requirements/traceability.csv`（或等效可查询数据）：需求 ID ↔ 任务 ID ↔ 代码变更 ↔ 测试用例 ↔ 验收证据，全程可追踪。

## 6. 角色体系与责任边界

角色是职责配置。每个角色必须有明确输入、输出、权限、工具和验收要求。质量决策尽可能由独立控制逻辑或工具结果判断，避免同一 AI 自写、自审、自测后自行宣布完成。

| 角色 | 主要职责 | 禁止事项 | 核心交付物 |
|---|---|---|---|
| 需求分析师 | 澄清需求、整理规格、识别歧义、维护需求追踪 | 不得擅自替用户确认关键业务规则；不得在需求不清时让开发角色自由猜测并大规模编码 | PRD、用户故事、验收标准、open-questions、追踪矩阵 |
| 架构师 | 技术选型、模块边界、数据流、接口和风险设计 | 不得绕过工程标准直接放任编码 | 架构图、ADR、API/数据契约、技术栈清单、风险清单 |
| 项目编排器 | 任务拆分、依赖管理、角色分派、进度和预算管理 | 不得把未通过门禁的任务标为完成；不应成为所有代码变更的唯一执行者 | 任务 DAG、调度记录、门禁执行记录 |
| 前端开发 | 按 UI/UX 约束、接口契约和前端规范实现 | 不得私自修改后端契约迁就实现 | 页面/组件/状态管理代码与测试 |
| 后端开发 | 业务逻辑、API、权限和服务层 | 不得自行改变已批准的需求或数据契约 | 服务代码、迁移、测试 |
| 数据库角色 | 数据模型、查询、迁移、完整性和性能 | 不得未经授权操作生产数据 | 数据模型、迁移脚本、查询与备份方案 |
| API/SDK 角色 | 统一接口封装、认证、错误处理和版本兼容 | 不得绕过安全或兼容性检查 | SDK、契约测试、Mock |
| 自动化测试（设计/执行） | 测试设计、执行、失败分析和回归验证 | 不得删除断言或跳过关键测试制造通过；执行必须运行真实命令而非仅读代码 | 测试计划、用例、机器可读结果与报告、失败证据 |
| 代码审查 | 可维护性、正确性、安全和规范符合度 | 不得仅凭主观判断代替机器测试；不得只给泛化结论 | 按严重度分级的结构化意见（文件/行号、影响、建议、是否阻断） |
| 集成修复 | 解决模块冲突、集成问题和跨模块缺陷 | 不得无审查地大范围重写；不得删测试/放宽断言/屏蔽错误来"修复" | 缺陷诊断、最小修复、回归验证记录 |
| DevOps/发布 | 构建、部署、环境配置、打包和交付 | 不得未经授权部署到生产环境 | 部署配置、健康检查、回滚方案、发布记录 |
| 安全审查 | 权限、依赖、密钥、输入处理和危险操作检查 | 不得把未检查的外部代码标为可信 | 安全审查报告、威胁模型、依赖审计 |
| 数据查询分析 | 识别数据来源与质量、设计查询与校验、数据导入导出与备份恢复 | 不将"能连接数据库"视为数据任务完成；生产数据读写严格授权与审计 | 查询设计、校验规则、测试/脱敏数据 |
| 文档角色 | 使用说明、架构文档、变更记录和交付报告 | 不得编造不存在的功能或测试结果 | README、架构/API 文档、变更日志 |
| 质量门禁控制器 | 读取机器检查结果并执行阶段准入规则 | 不得由执行代码的同一模型单方面豁免自身失败 | 门禁判定记录、例外审批记录 |

专业开发角色的语言变体（Python/Java/C#/.NET/TS 等）由语言适配器提供工程细节（见第 13 章）。动态组建团队：简单命令行工具只需需求、开发、审查、测试角色；复杂系统按需增加数据库、安全、运维、数据分析角色。**角色数量不是质量指标。**

## 7. 工程标准执行引擎（ESEE）

独立核心子系统，不直接承担业务功能开发，负责把项目规范应用到每个任务、每个角色和每次代码变更。

### 7.1 工程初始化（业务编码前强制完成）

按项目类型与规模生成并验证工程基线（脚本/CLI/桌面/Web 服务等使用不同模板，但每种模板必须定义最低工程要求）：

- [ ] 确认项目类型、目标平台、语言、框架及版本。
- [ ] 确认依赖管理、构建工具、运行时和最低运行环境。
- [ ] 建立标准目录结构。
- [ ] 配置格式化、命名规范、静态检查和类型检查。
- [ ] 建立测试框架、测试目录、测试数据和测试命令。
- [ ] 定义日志、异常处理、配置管理和密钥管理方式。
- [ ] 明确模块边界、接口契约、数据模型及错误处理约定。
- [ ] 配置 Git、分支/提交约定和可追溯变更记录。
- [ ] 配置依赖漏洞检查、许可证检查及适用的安全扫描。
- [ ] 建立统一质量检查入口（`check` / `test` / `build` 等命令）。
- [ ] 运行初始化验收，记录工具版本、检查结果和失败项。

**门禁：初始化验收通过后才允许进入正式业务编码。**

### 7.2 规则的可执行化结构

每条重要规范按以下结构管理：

1. 规则标识：唯一 ID、名称、适用范围。
2. 规则说明：要求什么、为什么。
3. 正例与反例。
4. 自动检查方法：格式化、静态分析、类型检查、测试或自定义验证器。
5. 严重程度：BLOCKER / MAJOR / MINOR / INFO（BLOCKER 为阻断）。
6. 豁免机制：必须写明理由、范围、审批角色、有效期。
7. 审计记录：规则版本、检查结果、豁免及原因。

无法自动检查的规则必须显式标记"人工/AI 审查项"，不得伪装成机器强制。

### 7.3 通用代码标准（规则内容来源）

- 职责单一、命名表达业务含义；输入、输出、边界和失败行为明确。
- 对外部输入验证；结构化错误处理，不吞异常、不用空捕获掩盖失败。
- 配置、密钥、环境差异不硬编码；日志可定位问题但不记录敏感信息。
- 资源正确释放；避免不必要的全局状态、隐式副作用和循环依赖。
- 公共模块有使用说明、接口约定和示例；改动必须同步更新测试与文档。
- 不得删除断言、跳过关键测试或伪造结果；不得未经授权修改无关代码。
- 依赖来自可信来源、版本可追踪，项目尽量可重复构建。
- 公共函数标准：单一职责；参数/返回/异常语义明确；边界与空值处理；副作用与 I/O 说明；超时、重试、幂等（适用时）；示例与测试；调用方与兼容性影响。各语言用等价机制（Python 类型注解＋docstring；TS 类型定义；Java 类型化签名＋API 文档；C# 类型＋XML 注释＋分析器）。
- 脚本标准：参数/配置/环境变量优先级明确；参数校验与帮助；成功/失败/部分成功退出码约定；结构化日志；超时、重试、取消与清理；幂等性说明；危险操作的预览、确认或 dry-run；测试与模拟外部依赖方法；运行平台与权限要求。
- API 标准：先定义请求、响应、认证、错误码、分页、超时和版本策略；维护机器可读契约（适用时 OpenAPI）；关键接口有契约测试与兼容性测试；调用方不得靠猜测字段依赖接口。设置连接/读取超时；有限重试＋退避；仅在语义安全时重试写操作；处理限流、分页、超大响应和非 JSON 错误；校验响应结构；记录关联 ID 与脱敏错误上下文。
- SDK/公共组件标准：封装认证、请求、重试、超时、日志和错误处理；统一命名与返回结构；明确版本兼容与弃用策略；新版本必须跑兼容性与回归测试。
- 数据库标准：版本化迁移；主键、外键、索引、唯一性、空值和完整性约束明确；参数化查询防注入；区分开发/测试/生产；关键数据变更有备份、回滚和验证方案；测试用可重置或隔离数据环境；生产数据删除或迁移属高风险，必须授权；密码不入仓库和日志。

### 7.4 质量门禁执行原则

- 阻断项失败时任务不得标记完成；未通过任务不得进入依赖它的后续任务。
- AI 不能把失败改写成成功；检查工具不可用时标记"未验证"而非"通过"。
- 所有门禁保存命令、工具版本、退出码、摘要和产物位置。
- 只有明确授权的角色能批准例外，并记录原因。
- 代码修改、依赖升级和配置变更必须重跑受影响的检查。

## 8. 标准研发工作流与阶段门禁

工作流实现为**可持久化的状态机**，不是对话中自由传话。12 个阶段及其门禁如下；门禁不通过不得进入下一阶段：

| 阶段 | 主要活动 | 关键交付物 | 门禁 |
|---|---|---|---|
| 0 环境与工程基线 | 检查目录、运行时、Git、容器、网络、模型接口；识别新/旧项目；创建配置、日志、状态存储；生成 PROJECT_CONTEXT.md；按 7.1 完成平台侧初始化 | 环境报告、工程基线、初始化验收报告 | 环境与初始化检查通过；工具缺失必须明确记录限制；不得默认执行危险全局操作 |
| 1 需求澄清 | 需求分析师按 5.2 与用户互动；建立草案、未知项、业务规则、风险和成功标准 | 需求草案、开放问题清单 | 关键需求得到用户确认；未确认项标记待定，不得当作事实 |
| 2 需求基线 | 生成正式 PRD、用户故事、验收条件、非功能要求、范围边界；记录确认时间、版本和变更 | 需求基线＋追踪矩阵 | 需求状态进入 APPROVED 并有版本记录 |
| 3 架构与技术方案 | 技术栈与选型理由；模块与目录；数据模型与迁移；API 契约与错误规范；安全边界与权限；配置/日志/监控/部署策略；测试策略；ADR；重大分歧向用户解释选项与代价 | 架构文档、ADR、契约、风险清单 | 关键架构决策、技术约束和主要风险有记录；不得由单一编码角色直接跳到实现 |
| 4 详细设计与任务拆分 | 拆分为小任务（唯一 ID、目标与需求 ID、前置依赖、允许修改范围、输入与适用规则、预期产物、契约、测试要求、验收条件、风险等级、所需权限）；依赖构成 DAG，发现循环先解决 | 模块设计、契约、测试计划、任务依赖图 | 每个任务有明确输入/输出/验收条件；关键契约已确认；高风险或重大成本计划需用户批准 |
| 5 契约与测试先行 | 在适当情况下先生成测试用例、接口契约、数据模型约束和模拟数据；开发与测试设计并行，但契约必须先达成一致 | 契约文件、测试用例、模拟数据 | 接口与数据契约经确认，避免各角色按各自假设实现 |
| 6 骨架与基础设施验证 | 建立最小可运行骨架：应用入口与配置、依赖注入（适用时）、数据库连接与迁移、契约桩、日志/异常/健康检查、测试入口、构建与启动流程 | 可运行骨架 | 骨架能按文档启动或执行；基础检查可运行；契约和关键基础设施得到验证 |
| 7 增量实现与并行开发 | 每次只领取一个边界清晰、依赖满足的任务；标准循环：读取需求/契约/规则→确认修改范围→补充测试→最小实现→格式/静态/类型/相关测试→审查与安全检查→记录变更与证据 | 任务产物、变更记录、证据 | 并行规则：仅依赖满足且契约稳定的任务可并行；文件/模块所有权明确；不得无协调同时修改同一关键文件；每个任务在独立分支/工作树/受控补丁中工作；合并前检查兼容性、冲突、测试与构建；上游契约变更时标记受影响任务并触发重验。开发遵循规范与既定架构，不得擅自换栈或重写无关模块 |
| 8 代码审核 | 审核角色获取需求、任务、diff、规范和测试证据，独立审核 | 结构化审查报告 | 阻断问题必须修复并重审；不采纳的建议记录理由，不得静默忽略安全或正确性问题 |
| 9 集成验证与缺陷循环 | 执行适用门禁：格式/lint、类型/编译、单元、集成、API/契约、端到端、安全与依赖、构建与启动、迁移验证、部署健康检查、必要性能/可访问性测试；缺陷流程：记录（严重度/证据/复现/关联需求）→根因诊断→最小修复→目标测试→回归测试→必要时重审；重试上限后升级，不得无限循环 | 测试报告、缺陷记录、回归证据 | 关键需求有对应测试或明确人工验收方式；未通过项进入缺陷流程；测试结果关联需求 ID、任务 ID、提交版本和环境 |
| 10 发布准备与打包 | 固定依赖与构建版本；跑全部必要门禁；检查敏感信息与不必要文件；生成构建产物与校验信息；验证安装/首次启动/升级/卸载（适用时）；生成运行、配置、备份和排查文档；记录已知缺陷 | 版本说明、部署配置、环境变量模板、回滚方案、验收清单 | 真实生产部署、对外发布、付费资源创建和数据变更必须按授权策略 |
| 11 最终验收与交付 | 质量门禁控制器依据证据决定交付；交付包：源码＋锁定依赖、README 与快速启动、`.env.example`（无真实密钥）、架构/接口/数据库文档、测试报告与质量检查结果、部署/升级/备份恢复/回滚说明、已知问题与未验证项、追踪矩阵、版本号与变更记录 | 交付包＋验收报告 | 所有强制门禁通过、阻断缺陷关闭、交付文件齐全才可标 DELIVERED；经用户明确接受的例外必须标"带条件交付" |

标准循环：`需求确认 → 架构规划 → 任务拆分 → 测试设计 → 开发 → 代码审核 → 自动化测试 → 缺陷修复 → 回归测试 → 集成验收 → 部署准备 → 交付`。审核/测试失败返回相关步骤；需求变更时重新评估架构和任务依赖。

## 9. 任务状态机、循环控制与失败处理

### 9.1 任务状态（10 态）

`DRAFT`（草拟）→ `READY`（输入/依赖/验收齐备）→ `IN_PROGRESS`（执行中）→ `REVIEW_REQUIRED`（等待审查）→ `TEST_REQUIRED`（等待测试）→ `PASSED`（全部必需门禁通过）；旁路态：`BLOCKED`（依赖或环境阻塞）、`FAILED`（检查或执行失败）、`REWORK`（返工中）、`CANCELLED`（经授权取消）。

### 9.2 状态转移规则（由控制器依据证据触发，不接受 AI 自报状态）

- `READY → IN_PROGRESS`：前置依赖通过，执行权限可用。
- `IN_PROGRESS → REVIEW_REQUIRED`：实现产物已生成，基础检查完成。
- `REVIEW_REQUIRED → TEST_REQUIRED`：审查无阻断问题。
- `TEST_REQUIRED → PASSED`：必需测试全部通过且证据已保存。
- 任一必需门禁失败：转 `FAILED` 或 `REWORK`。
- 重试超限、权限不足或关键决策缺失：转 `BLOCKED` 并请求处理。

项目级状态由子任务和阶段状态汇总生成，不能由总控 AI 单方面宣布"项目完成"。

### 9.3 循环控制与防失控

- 每个任务设置最大重试次数和时间/Token/成本预算。
- 失败后优先根因分析，不无条件重复同一操作；相同错误连续出现触发升级。
- 检测无进展循环、相互矛盾的 Agent 结论、测试反复抖动和依赖无法安装。
- 外部服务调用设置超时、退避重试和速率限制。
- 支持人工暂停、恢复、取消或批准继续。
- 所有循环记录尝试次数、变更差异、结果和成本。
- 达到停止条件后给出清晰报告，不得假装任务完成。

### 9.4 交付停止条件

以下条件必须满足或有用户批准的例外：已批准需求有对应实现或明确未实现说明；强制验收条件有验证证据；阻断与严重缺陷已关闭；编译/构建成功；适用测试通过；安全门禁通过或风险被正式评估并获授权接受；部署说明可复现且状态如实；文档与交付产物齐全；工作区、版本、变更和已知限制清楚可查。

## 10. 知识库与治理

知识库是受版本管理和可信度管理的工程资产库，不是把所有内容塞进一个向量库。

### 10.1 知识分层（9 层）

1. 平台级强制规范：安全、权限、任务协议、质量门禁、交付要求。
2. 项目类型模板：Web、桌面、移动、命令行、数据处理、自动化测试等。
3. 语言与框架规范：按语言和版本分区，标注适用版本、来源、更新时间、可信等级和适用范围；版本不明的内容不得覆盖项目当前标准。
4. API/SDK 与公共组件：调用方式、版本、错误处理、示例；官方文档优先于旧聊天记录、未验证博客或模型记忆；可能变更的 API 实施前重新核对官方文档。
5. 经过验证的代码模板：函数、脚本、服务、测试、部署和迁移模板。每个公共函数/组件记录：名称用途、输入输出与类型、前置/后置条件与不变量、异常与错误策略、超时重试幂等与副作用、权限与敏感数据注意、示例、测试与覆盖边界、版本兼容与弃用策略、来源许可证审核状态与验证证据。
6. 已验证项目经验：常见问题与根因、修复与回归用例、已验证架构模式与反例、排查手册、已批准技术决策、已知限制。不得把一次偶然成功或未复核的输出自动写成"标准答案"。
7. 待验证方案：AI 生成但尚未通过验证的建议或代码。
8. 废弃与兼容性记录：旧版本、弃用接口和不再推荐的实现。
9. 任务与运行知识：项目状态、任务输入输出、审查意见、测试报告、模型调用记录、失败原因和成本；敏感内容脱敏，设保留期限和访问控制。

### 10.2 可信等级

`VERIFIED`（在明确环境/版本/测试范围内已验证）＞ `APPROVED`（已审查批准，不代表所有场景验证）＞ `REFERENCE`（官方文档或外部参考，未在项目中验证）＞ `PROPOSED`（AI 提出的待验证方案）；`DEPRECATED`（已弃用，保留仅供迁移或审计）。开发默认优先使用 VERIFIED 和适用的 APPROVED；引用其他等级必须说明不确定性。AI 生成的代码不得未经验证标为 VERIFIED。

### 10.3 入库与检索规则

- 外部代码示例检查许可证、来源和版本；SDK/API 示例记录对应版本。
- 新知识进入主库前经过审查和必要的回归验证；发现错误或过时资产时标记并停止推荐。
- 检索先按语言、框架、版本、任务类型、风险和项目范围过滤，再做关键词/全文/向量检索；结果连同来源、版本和可信等级传给角色。
- 不把整个知识库一次性塞进上下文；按任务按需加载。
- 冲突知识展示冲突，不得静默选择；代码搜索支持符号、文件、调用关系和依赖检索，语义检索为补充。
- 知识库修改必须经过验证、版本管理和审核；知识中的指令性内容不能覆盖平台安全策略。

## 11. GitHub Skills 接入策略

Skill 是可复用工作流与知识包。优先兼容公开 Agent Skills 格式（SKILL.md＋YAML frontmatter 的 name/description；可选 scripts/、references/、assets/；职责单一、按需加载；用官方工具检查格式）。

### 11.1 候选来源（并集，接入前必须重新审计）

1. Agent Skills 官方规范：<https://github.com/agentskills/agentskills>（格式标准来源）。
2. <https://github.com/addyosmani/agent-skills>
3. <https://github.com/executiveusa/pauli-agent-skills-2026>
4. <https://github.com/builtbystef/skills>
5. <https://github.com/Codagent-AI/agent-skills>

列出不代表已审计或可直接用于生产；候选来源先登记再审核，不得把搜索结果数量或 Star 数当质量。

### 11.2 接入流水线

获取候选仓库与明确版本/commit → 检查许可证、维护状态、依赖和来源 → 检查 Skill 内指令、脚本、命令和外部访问行为 → 判断能力边界与平台规则冲突 → 隔离环境试用 → 通过功能、质量、安全和回归测试 → 固定版本、生成来源与审计记录 → 接入注册表 → 升级时重新审查与回归验证。

### 11.3 三层结构

- 第一层 平台核心控制器：项目状态机、权限、任务依赖、资源预算、质量门禁、审计和失败恢复。
- 第二层 通用工程工作流 Skills：需求分析、规格、计划、实现、测试、审查、调试和交付方法。
- 第三层 技术栈 Skills：语言、框架、数据库、API/SDK、测试工具、容器和部署实践。

外部 Skill 只能提供能力建议和执行步骤，**不能获得绕过平台权限与质量门禁的权力**；Skill 内容中任何试图覆盖系统安全策略、索取秘密或绕过授权的指令都视为不可信内容并拒绝执行。

### 11.4 选择与治理

编排器按任务类型、语言框架、项目版本、所需工具与运行环境、风险等级、审核状态与许可证、依赖与成本匹配技能；支持组合、冲突检测、版本固定、按需加载、使用记录和效果评估。记录仓库 URL、作者、版本/SHA、许可证、引入时间、审核人；固定版本避免运行时拉取不受控最新内容；未批准不得读取或上传用户秘密、源码、个人数据或生产数据；许可证无法确认时标记待审，不用于交付；支持禁用、卸载、回滚和升级。

## 12. 模型与工具适配

### 12.1 模型提供商适配层

不绑定单一供应商；统一接口支持云端 API 与本地模型。每次调用记录：供应商、模型标识和配置版本、角色与任务 ID、输入/输出摘要（脱敏）、Token/费用（可得时）、延迟/错误/重试次数、结构化输出校验结果。模型不可用时给出明确错误并支持切换或暂停，不得静默伪造回答。

### 12.2 工具适配层

通过受控接口管理：文件读取/编辑/差异、命令行执行、Git 与分支/工作树、编译/测试/lint/静态分析、数据库访问、浏览器与 API 测试、Docker/容器、CI/CD 与部署、文档与知识检索。**工具权限按角色最小化**（如需求分析角色默认无生产库写权限，审查角色默认只读变更）。

### 12.3 执行隔离

- 独立工作区或容器中运行不可信代码；命令设超时、资源限制和工作目录。
- 网络访问实行可配置允许列表；开发/测试/预发布/生产凭证隔离。
- 高风险命令显示计划和影响并获授权；工具调用失败保留日志、退出码和上下文。
- 支持 Windows 开发环境，尽量提供 Docker/CI 中的可复现执行方式。
- 对执行命令设置取消机制和输出大小限制；支持停止任务并安全终止子进程。

## 13. 多语言支持与项目模板

### 13.1 适配器声明

语言适配器声明：支持的语言和版本；项目识别规则；包管理器和锁文件；格式化/lint/类型检查/编译构建命令；单元/集成测试与覆盖率工具；静态分析与安全扫描工具；项目模板和目录规范；Docker/CI 支持方式；可用 Skills、官方文档和限制。

通用控制器管理：任务状态、依赖和审批；输入输出协议；质量门禁；日志、审计和成本；文件与工具权限；交付物管理。**统一的是任务格式、质量门禁、状态机、证据和交付标准，不是要求不同语言用相同目录结构或工具**（不建立虚假的跨语言统一）。

### 13.2 支持批次

1. 第一批：Python、JavaScript/TypeScript，以及 REST API 与常见数据库的测试集成能力。
2. 第二批：Java、C#/.NET。
3. 后续：Go、Rust、PHP、Ruby、Kotlin、Swift 等按真实需求扩展，通过适配器接入，不修改核心。

### 13.3 混合技术栈

必须支持一个项目多技术栈（如 React/TS 前端＋Java/C# 后端＋Python 测试＋PostgreSQL/MySQL＋Docker）。每个模块明确运行时、版本、接口协议、构建顺序和部署关系；编排器按模块识别语言分派任务，通过 API 契约、集成测试和部署测试验证整体。

## 14. 平台自身架构

### 14.1 模块边界

采用模块化单体起步，边界清晰，未来按瓶颈拆分，不机械微服务化：

- `apps/cli`、`apps/desktop`：命令行驱动与 Windows 桌面 UI。
- `core/domain`：核心领域模型（项目、需求、任务、证据）。
- `core/orchestrator`：任务调度、DAG、重试、暂停恢复。
- `core/workflow`：阶段流程与门禁状态机。
- `core/standards`：工程标准执行引擎（ESEE）。
- `core/quality`：测试与质量检查、证据管理。
- `core/security`：权限与安全策略。
- `core/audit`：审计与运行记录。
- `adapters/models`：云端/本地模型适配器（含模拟适配器）。
- `adapters/tools`：文件/终端/Git/测试/浏览器受控工具。
- `adapters/languages`：python / javascript-typescript / java / dotnet。
- `adapters/databases`、`adapters/packaging`：数据库与安装发布适配器。
- `agents`：角色配置（提示词、输入输出协议、权限）。
- `skills`＋`skills/registry.yaml`：平台自有技能与注册表。
- `knowledge`：分层知识库与外部技能治理台账（skills-registry）。
- `schemas`：任务协议、项目状态、产物格式的 JSON Schema。
- `templates`：不同项目类型的初始化模板。
- `config`：platform / models / policies / quality-gates / language-adapters 等集中配置。
- `runtime`：state / logs / artifacts / checkpoints（按配置存储，敏感与大体积数据不入 Git）。
- `tests`、`docs`、`scripts`、`packaging`、`.github/workflows`、`examples/sample-projects`。

### 14.2 统一目录结构（基线，可在 ADR 中调整，保留职责清晰、配置集中、测试齐全、文档完整原则）

## 15. 本地安装与双重交付

### 15.1 概念区分

**本地安装**（平台装在用户电脑上）、**本地执行**（代码/测试/Git/构建在本地或授权环境运行）、**云端模型**（API 调用，受网络/授权/费用/服务限制）、**本地模型**（调用本机模型，有硬件要求）、**完全离线**（除安装外全部无网可用）——五者相互独立，不得混用宣传。

### 15.2 平台自身安装包（Windows 首要目标）

必须定义并验收：安装与卸载方式；应用与运行时依赖；配置/日志/缓存/项目文件存储位置；API 密钥或本地模型配置流程；权限与安全提示；版本升级与数据迁移；崩溃日志与诊断导出；安装后首次启动验证；干净环境安装测试；断网、模型不可用、磁盘不足等失败场景。打包技术在技术选型阶段比较后确定（ADR），不在需求未清时锁定框架。

### 15.3 用户项目交付形式

按目标项目类型选择：Windows 桌面应用（安装程序或便携产物）；Web 系统（源码、构建产物、部署配置、运行说明）；后端服务（可重复构建的程序包、容器镜像或部署包）；Python 工具（源码、锁定依赖、适用时可执行打包）；Java 项目（可执行 JAR、服务器包或镜像，按需求）；C#/.NET（框架依赖或自包含发布，按需求）；自动化测试项目（测试代码、环境说明、执行命令、报告与数据准备方法）。**不承诺每种项目都能生成单一安装包**；交付形式由需求、平台、技术栈和部署环境决定。

### 15.4 桌面 UI 要求

用户应能：创建项目并输入想法；查看/确认/修改需求分析；查看架构、任务树和依赖；查看每个角色当前职责、状态和输出；查看失败原因、审查意见和测试报告；批准/拒绝/要求修改计划；暂停、恢复、取消、重试工作流；查看费用、运行时间和工具调用记录；查看项目文件、diff 和交付物；管理 Skills、知识来源、模型配置和权限策略。界面必须反映真实工作状态，不得做"输入一句话—显示思考中—输出文本"的假界面。

## 16. 测试策略与质量门禁

### 16.1 测试层级（按项目类型组合）

单元（函数/类/局部规则）、组件（模块内交互）、集成（数据库/缓存/队列/外部服务/协作）、API/契约（请求/响应/错误/兼容）、端到端（真实用户流程）、回归（修复不破坏既有）、安全（授权/输入/敏感数据/依赖）、性能与可靠性（明确的服务等级要求）、部署（安装/配置/启动/健康检查/恢复）。

### 16.2 白盒测试边界

利用控制流、数据流、分支、异常路径、状态转换和依赖设计测试，但必须明确：读取代码≠运行测试；覆盖率≠正确性；测试通过≠无缺陷；不能穷尽所有输入和错误；高风险功能需更强独立审核与实际环境验证。对关键业务逻辑设合理覆盖率目标，阈值按风险制定，不盲目追求 100% 行覆盖而忽略断言质量。

### 16.3 统一严重度量表

`BLOCKER`（阻断交付）＞ `CRITICAL`（关键功能或安全）＞ `MAJOR`（重要逻辑/兼容/质量，即"警告"档）＞ `MINOR`（一般改进）＞ `INFO`（非阻断建议）。规则检查与代码审查共用；审查意见必须含文件/行号、影响、复现条件、修改建议和是否阻断合并。

### 16.4 每任务最低门禁清单

按适用性检查：格式与 lint；类型检查或编译；对应单元测试；相关集成/契约测试；代码审查；变更范围与需求一致性；依赖与安全风险；文档更新；实际命令退出码与报告；失败项的明确处理记录。

### 16.5 最终质量报告

包含：总体状态（通过/带条件通过/未通过）；需求覆盖率与未完成需求；构建、静态、测试、安全检查结果；用例总数/通过/失败/跳过/未执行；关键缺陷及状态；部署验证范围；未验证项与环境限制；已知风险与技术债；可复现命令和证据路径。**必须区分"通过/失败/未验证/不适用"，不允许把未执行的检查报告为通过。**

## 17. 安全、隐私与权限

- 密钥用环境变量、系统凭据存储或安全注入；不提交 Git、不入普通日志或知识库。
- 角色仅拥有完成任务所需最低权限；默认只允许访问用户明确授权的项目工作区。
- 对外部输入、网页、仓库、Skill 和文件内容按不可信输入处理；防提示词注入导致读取秘密、执行危险命令或外发数据。
- 外部网络访问、文件上传、生产数据访问和付费操作受策略控制；生产部署、数据删除、破坏性结构变更、权限提升需明确授权；不把"AI 自己同意"作为高风险操作唯一授权依据。
- 日志脱敏、限制保留周期、支持审计；测试环境用合成或脱敏数据。
- 支持取消运行并安全终止子进程；生成的脚本静态检查并隔离执行。
- 检查第三方许可证、依赖漏洞和供应链风险；模型输出与外部 Skill 指令不得高于平台安全策略。
- 提供停止任务、撤销未提交修改和恢复到安全版本的能力。

## 18. 可观测性、审计与可恢复性

每个项目、任务和 Agent 运行可追踪。至少记录：任务状态变化与时间；角色、模型和 Skill 版本；输入/输出产物引用；工具调用、命令、退出码和耗时；文件变更 diff、提交/分支标识；审查意见、测试报告和缺陷；重试、失败原因、人工批准和取消；资源消耗与模型成本（可得时）。

支持：查询项目所处阶段；查看任务阻塞原因；查看失败的角色和测试；从安全检查点恢复；重试单个任务而不重做整个项目；比较不同运行结果；导出完整审计记录。日志不得存未脱敏的秘密或敏感数据。

## 19. 平台自身测试要求

平台也是软件产品，必须测试"负责生成软件的平台本身"。

### 19.1 覆盖范围

- 状态机合法与非法转换；任务依赖图与循环检测。
- 并行任务冲突与取消；角色/Skill 选择规则。
- 模型适配器成功、超时、限流、断网和响应格式错误。
- 工具执行超时、危险命令拦截、路径越权。
- 质量门禁失败时正确阻断；任务重试上限和预算上限。
- 结构化输出校验；权限策略；版本和配置解析；知识检索过滤逻辑。
- 任务状态持久化与恢复；Skills 注册、版本固定和安全校验。
- 产物存储、检索和审计；多角色任务交接；测试报告与缺陷回传。
- 审计日志完整性与敏感信息脱敏。
- 项目暂停、恢复、崩溃后续跑和部分产物清理。
- 平台安装、升级、卸载和配置迁移；构建结果与测试报告一致性。
- 用户项目的需求追踪和交付完整性。

### 19.2 端到端验收场景（至少 10 个）

1. 用户提交模糊想法，需求角色询问并形成草案。
2. 用户确认需求后，系统生成架构和任务计划。
3. 系统生成一个小型但完整的真实软件项目。
4. 自动执行构建、测试、审查和报告生成。
5. 人为引入缺陷，确认测试能发现并触发修复循环。
6. 模拟模型或工具调用失败，确认系统能记录、重试或暂停。
7. 任务中途停止系统，重启后能恢复。
8. 确认未授权操作会被阻止。
9. 验证 Skills 版本固定和不可信指令处理。
10. 验证最终报告不会把未执行的测试写成通过。

## 20. 成功指标

按项目类型解释，不可只看单一数字；**指标不得诱导作弊**（不得靠减少测试提高通过率，不得靠降低审查严格度减少缺陷数）：

- 规范符合率：新代码通过必需静态检查和规则门禁的比例。
- 需求澄清后返工率；需求到任务的可追踪率；需求覆盖率（需求↔实现↔测试↔证据追踪完整度）。
- 任务验收通过率；构建成功率（规定环境中可重复构建）。
- 测试执行率与失败率；测试真实性（命令、退出码、结果可追溯，未执行不报通过）。
- 缺陷逃逸率与回归失败率；代码审查发现的严重问题数。
- 未授权操作拦截率；工作流中断后恢复成功率；恢复能力（失败后能否安全暂停/恢复/转人工）。
- Skills 复用率和技能有效性；返工率（任务定义不清、接口冲突、规范缺失导致的重复工作）。
- 每任务/项目的耗时与模型成本；资源可控性（预算、执行时间、并发、存储可限制）。
- 人工介入次数及原因；交付文档完整率；部署复现成功率；安装成功率（干净环境安装/启动/卸载）。

具体目标值在试点阶段用真实项目建立基线后再定门槛，不虚构高成功率承诺。

## 22. 执行 AI 的工作要求

1. 先阅读并对照两份源规范与本合并版，列出重复、冲突、缺失条款；有异议按《01-冲突与遗漏分析.md》申诉，不得静默偏离。
2. 不要直接开始大量编码。先检查现有仓库和环境，输出架构、任务依赖图、阶段计划和风险清单；与用户确认《03-实施计划.md》附录中的关键决策（D1–D10）。
3. 优先实现工程标准执行引擎、项目状态机、质量门禁和最小研发闭环；业务代码生成前先建项目模板、规则配置、测试框架、日志和构建流程。
4. 每个任务必须有明确输入、输出、依赖、修改范围和可验证的验收标准；所有生成代码遵循项目规则并运行适用自动检查。
5. 不把未运行的测试、未执行的构建或未审查的技能标记为通过；不无限重试，达到上限即停并说明阻塞原因。
6. 不未经授权访问工作区以外文件、泄露密钥、删除用户数据或部署生产环境。
7. 外部 Skill、依赖和代码模板必须审查来源、许可证、版本、权限与安全性；对每次修改保留可追溯记录，优先 Git 小范围提交。
8. 先完成一条端到端真实闭环，再扩展更多角色、语言和技能。
9. 平台自身必须有单元、集成、端到端、安全和安装测试。
10. 最终报告清楚列出已完成、未完成、已验证、未验证、已知缺陷和交付文件；不能只交付架构图、提示词或演示页面。
11. 每阶段结束报告：完成内容、修改文件、执行过的命令、测试证据、失败项、已知限制和下一阶段计划。
12. 当前环境不支持多模型并发时，先实现可插拔角色与编排机制，用单模型多角色或模拟适配器验证流程，不宣称真实多模型并行；无法访问 GitHub 或模型 API 时，先建可运行本地基础，外部接入标记未完成，不编造结果。
13. 遇需求不清、重大技术影响或高风险操作，先向用户提问，不把猜测写成已确认需求。
14. 最终目标不是让 AI 看起来像研发团队，而是让系统真正按软件工程流程，把想法转化为有规范、有测试、有审查、有部署方案、有验证证据、可持续迭代的标准项目。

## 附录 B：开发前待确认决策（暂定默认值，须用户确认后方可作为基线）

| # | 决策 | 暂定默认（标记为"暂定"） |
|---|---|---|
| D1 | 首要操作系统 | Windows 优先（开发与交付均以 Windows 为第一目标） |
| D2 | 第一版支持的项目类型 | 命令行工具 / 后端服务小项目模板先行，Web 与桌面模板随后 |

| D4 | AI 权限边界 | 默认仅授权项目工作区＋命令白名单/超时；安装依赖、访问外网、危险命令按风险审批 |
| D5 | 联网策略 | 允许联网（模型调用、依赖安装、文档获取）；秘密与用户数据不出本地 |
| D6 | 首批语言优先级 | Python → JavaScript/TypeScript → Java → C#/.NET |
| D7 | 多项目并行/远程执行 | 第一版单项目串行，架构预留多项目与远程执行 |
| D8 | 平台与项目交付平台 | 平台 Windows 安装包；用户项目按类型决定交付形式 |
| D9 | 用户必批点 | 需求批准、计划批准、高风险操作授权、最终交付四个必批点；低风险任务自动执行 |
| D10 | 资源预算 | 第一版记录用量不强制限额；预算配置化预留（时间/Token/并发） |

> 上述默认值仅用于技术验证；正式基线前必须经用户确认并记录于 ADR。
