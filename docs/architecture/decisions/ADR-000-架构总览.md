# ADR-000：平台总体架构

- 状态：已接受
- 日期：2026-10-21
- 关联：ADR-001（存储）、ADR-002（模型接入）、ADR-003（基线决策）

## 背景

平台是「AI 软件研发控制系统」而非提示词集合（规范 §1.1）：流程由系统控制、门禁由执行器强制、证据可复查。需要确定分层与模块边界，作为 Phase 1 起所有实现的骨架依据。

## 决策

采用**核心—适配器—应用三层**架构，目录基线遵循规范 §14.2：

```
apps/（cli、desktop）      应用层：开发期 CLI 驱动；产品形态 Windows 桌面 UI
core/                      核心层（纯业务规则，不依赖具体技术）：
  domain/                    实体与协议（Project/Task/Review/Defect…，规范 §14.3）
  orchestrator/              任务 DAG、调度、预算与循环控制（规范 §9.3）
  workflow/                  12 阶段工作流状态机（规范 §8）
  standards/                 ESEE：规则加载、注入、检查编排（规范 §7）
  quality/                   质量门禁判定与严重度量表（规范 §16）
  security/                  权限、白名单、危险操作拦截（规范 §17）
  audit/                     审计日志、脱敏、可追溯（规范 §18）
adapters/                  适配层：models/tools/languages/databases/packaging
agents/                    角色配置（职责/权限/验收要求，规范 §6）
skills/ + knowledge/       可复用能力与受治理知识（规范 §4.7、§10）
schemas/                   跨角色 JSON Schema 协议（规范 §14.4）
config/                    全部策略与门禁的集中配置（先定标准，再写代码）
```

## 备选方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 核心—适配器—应用三层 | 门禁/状态机可独立测试；模型、语言、打包可替换；与规范 §14.2 一致 | 初期结构成本略高 | **采用** |
| B. 单体脚本 + 提示词集合 | 起步快 | 违反规范 §1.3「流程由系统控制」；无法防 AI 谎报；不可演进为桌面产品 | 拒绝 |
| C. 微服务化（进程拆分） | 隔离好 | 本地桌面产品过度设计；部署/调试复杂 | 拒绝（进程内模块化即可） |

## 结论

1. core 层不 import 任何 adapters/apps；依赖方向 apps → core →（协议）→ adapters。
2. 角色不绑定独立模型/进程（规范 §2）：同一模型可承担多角色；角色间用 schemas/ 协议通信，不传自然语言。
3. Phase 1 先实现 core（状态机/DAG/持久化/审计）＋模拟模型适配器；apps/cli 与真实模型随后。
4. 桌面 UI（P7）与打包技术（D8）在对应阶段以独立 ADR 确定，此处不锁定。
